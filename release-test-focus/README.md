# Release Test Focus

Compiles the two kinds of changes in a release — **main-project code changes** (tickets behind PRs) and **dependency-library upgrades** (their tickets) — into a tester-facing brief: an overview with overall risk up top, must-test priorities in the middle, and full change lists by source at the bottom, linked by clickable anchors.

**Division of labor:** semantic work (reading descriptions, generating the test focus) is done by the LLM; mechanical work (priority mapping, must-test selection, sort, risk, rendering) is done by the script reading `rules.ini`. Rules live only in `rules.ini` — SKILL.md and the script stay fixed.

## Directory structure

```
release-test-focus/
  SKILL.md                   # Main workflow (read by the AI)
  README.md                  # This file (read by human maintainers)
  rules.ini                  # Single source for mechanical rules (mapping/must-test/sort/risk/nav)
  scripts/
    render_brief.py          # tickets.json + rules.ini -> release-test-focus.md
  examples/
    sample-tickets.json      # Sample input
```

## Dependencies

- Python 3.7+
- **No third-party dependencies** — Python standard library only (`configparser` parses `rules.ini`).

## Quick start

1. Prepare `tickets.json` following `examples/sample-tickets.json` (each ticket's `focus` is generated by the LLM first).
2. Run:

```bash
python scripts/render_brief.py tickets.json [-o release-test-focus.md]
```

3. You get a Markdown brief with a table of contents and clickable anchors.

## Input format (tickets.json)

```json
{
  "meta": { "version": "v2.4.0", "baseline": "v2.3.2", "window": "2026-07-01" },
  "tickets": [
    { "id": "ENG-1024", "title": "New payment flow", "description": "...",
      "type": "Story", "priority": "blocker", "source": "main", "focus": "..." },
    { "id": "LIB-221", "title": "Upgrade auth-sdk", "description": "...",
      "type": "Defect", "priority": "critical", "source": "dependency",
      "library": "auth-sdk", "version_from": "1.8", "version_to": "2.0", "focus": "..." }
  ]
}
```

- `type`: `Story` or `Defect`
- `source`: `main` or `dependency`
- `priority`: your **team's real naming**; `rules.ini`'s `priority_mapping` maps it. A value missing from the mapping makes the script error and tell you to add it.
- `focus`: the test-focus line, generated by the LLM beforehand.

## Customizing rules (edit only rules.ini)

`rules.ini` is the single source for mechanical judgments. Common adjustments:

| Want to change | Where |
|---|---|
| Different team priority naming | `priority_mapping`: format `<name> = <tier>:<weight>`; replace left-hand keys with your real values |
| Must-test threshold / which sources are always must-test | `must_test.priority_weight_min` / `must_test.sources` |
| Breaking-change keywords | `must_test.description_keywords` |
| Must-test table ordering | `type_order` / `source_order` (sort keys are fixed) |
| Overall risk thresholds | `risk` |
| TOC / anchors / back-to-top | `nav` |

> Changing rules never requires touching SKILL.md or the script.

## Common mistakes

| Mistake | Fix |
|---|---|
| Editing the script or SKILL.md to change logic | Edit only `rules.ini` |
| Using a priority in tickets.json that rules.ini doesn't map | Add that name to `priority_mapping` |
| Passing the ticket description as `focus` | `focus` must be distilled by the LLM into "what to test" |
| Expecting only high-priority dependencies in the brief | Dependency upgrades are must-test by default (wide regression surface) — see `must_test.sources` |
