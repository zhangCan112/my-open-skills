# TDD 报告：designing-workflows

**日期：** 2026-07-02
**对象：** `designing-workflows/SKILL.md`
**方法：** writing-skills 的 RED-GREEN-REFACTOR，subagent 对照实验（同场景：无 skill vs 有 skill）

## 测试场景

两个独立场景，覆盖 6 个失败模式。每个场景给定**受控能力集**（观察是否虚构/误分类）。

- **场景1**：用 AI 给代码改动自动写 commit message（测试：定义终点 / 缺口 / 最简优先）
- **场景2**：用 AI 做竞品分析报告（多竞品×多维度+图表）（测试：分层/平铺 / 编排复杂度）

## RED 基线（无 skill）—— 实测失败

| 失败模式 | 场景1 | 场景2 |
|---|---|---|
| **#2 平铺 god object** | ✗ 10 阶段全塞进**一个扁平 deliverable**，无目录/无懒加载 | ✗ 6 阶段 + 多 JSON schema 全平铺 |
| **#5 过度编排** | ✗ 给 commit msg 造 10 阶段 SCU 流水线 | ◯ 偏重，但任务确实复杂 |
| #1 定义终点 | △ 列了假设，非 gated Phase 0 | △ 有 Stage0 但非确认终点 |
| #4 缺口分析 | △ 揉进"假设" | △ 同 |
| #3 误分类 | ✓ 守规矩 | ✓ 守规矩 |
| #6 虚构能力 | ✓ 守规矩 | ✓ 守规矩 |

**关键发现：** 真实痛点是 **平铺输出 + 过度编排**。原本担心最严重的"虚构能力"，实测 agent 本来就守规矩——说明 skill 的价值落点正确，但"虚构能力"那条属于预防性条款（2 个场景不足以下结论，保留）。

## GREEN（有 skill）—— 验证通过

| 失败模式 | 场景1 GREEN | 场景2 GREEN |
|---|---|---|
| 平铺 god object | ✓ 目录：flow.md + 4 step + gaps.md | ✓ 目录：flow.md + 5 step + gaps.md |
| 过度编排 | ✓ **4 phase prompt 链**，明写"最简优先，不套多 agent" | ✓ 论证"单次 LLM 取不到外部数据，链式为必要复杂度" |
| 定义终点 | ✓ Phase 0 成功标准/约束/消费模式 | ✓ Phase 0 |
| 缺口分析 | ✓ Phase1 初扫 + Phase5 填平 + gaps.md | ✓ 8 条缺口留痕 |
| 误分类/虚构 | ✓ | ✓ |

两 agent 都走完六阶段、做了 DoD 五项自检、引用 skill 条目、正确地把盘点到但不用的能力（如 `writing-skills`）排除。**核心失败模式被纠正。**

## REFACTOR —— 测试暴露的真问题

两个 GREEN agent 都撞到同一个 skill 未定义的情况：**一次性/非交互产出**时，Phase 0/3 的"用户确认"gate 和 Phase 5 访谈没有交互对象。它们自行用"显式默认 + 留痕 + 标最不确定"绕过——但 skill 没说明这种模式，不够谨慎的 agent 可能卡住或悄悄跳过。

**修补：** 在 SKILL.md 六阶段后新增"非交互模式（一次性产出）"小节：用显式默认推进、gaps.md 留痕、标最不确定项、开头声明。并明确"默默假设而不留痕 = 跳过 gate，违规"。

## 结论

- RED 证实真实失败是**平铺 + 过度编排**（非虚构能力）
- GREEN 证实 skill 纠正了这些失败
- REFACTOR 修补了非交互模式的 gate 处理漏洞
- 状态：**GREEN 达成**。建议后续用更复杂场景（如多 agent 编排类目标）继续压测，扩展样本。
