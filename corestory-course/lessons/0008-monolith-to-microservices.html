Monolith to Microservices（单体拆微服务）

企业最常见的现代化模式——也是失败率最高的那一个。本课讲服务边界、数据库拆分与 strangler 执行。

为什么叫"最难的模式"

拆服务失败的团队往往做出一个比原来更糟的分布式单体：服务被数据库紧绑、同步调用过时、独立部署只是想象。CoreStory 在此的价值：浮出单体真实的内部结构（耦合模式、数据访问热点、隐式依赖），而不是团队成员脑中的想象。来源

每次服务抽取的六步走法

  1. Context Loading — 从阶段四对话载入工作包（WP-XXX）+ 依赖、阻碍项、TCE 计划、验收标准。建 [Extraction] 系统名 - 服务名 (WP-XXX) 对话。
  2. Service Boundary Identification — 精确划定边界：对模块递归标记 MOVE / SHARE / LEAVE；找隐身耦合（两个方向的直调、共享内存态/单例、共享 config、DB 触发器/存储过程/视图、事件处理器）；验证双方都能独立运转（检查循环依赖）。
  3. Database Decomposition Planning — 映射数据所有权（owned / read-only / shared-write；外键、跨边界 join）。用决策树选拆分策略（见下表）。这是最难的战场。
  4. Façade & Communication Design — 枚举入口点（HTTP 路由、内部方法调用、后台任务、事件处理器、CLI），设计每类交互走网关/反向代理/适配器；选同步（REST/gRPC）还是异步（事件）；设计防腐蚀层（Anti-Corruption Layer）——单体模型与服务模型之间的翻译层，是临时的，注定要被移除。
  5. Extraction Execution — 按 delta spec 建独立新服务（Transform）→ 配置 facade 路由 + 影子请求对比 + 定向流量（Coexist，配好错误率/时长监控与熔断回退）→ 行为验证通过后退役（Eliminate：删单体旧代码、改路由拆除、清理 ACL、更新测试）。
  6. Verification & Cutover — 拆除后：复核单体与服务差异、逐条集成点、DB 迁移与全量/冒烟负载，然后改名对话 RESOLVED。

数据库拆分策略（决策树）

情形推荐策略
单写者 + 适合读API-mediated access（通过 API 读取，不共享表）
高频读、容忍最终一致CDC / 事件驱动同步（Debezium、AWS DMS）
可合并为单写者Refactor to single writer
真共享状态共享 schema 合租（保持表在同一 schema）

并发期间交叉边界外键：小心处理；回滚要有计划。

分布式事务：Saga 与 Outbox

分布后，跨两库的单事务是常见失败。两种工具：

  • Saga（长按事务编排）：Choreography（无中心，事件驱动，适合 2–3 服务）vs Orchestration（中央协调器，适合 4+ 复杂流程；工具：Temporal、AWS Step Functions、Camunda、Azure Durable Functions）。
  • Outbox pattern：把"要发的事件"和业务写进同一个 DB 事务，随后由发布者读取发出 → 避免双写时的双振断流，配合幂等消费者保证性地至少一次。用 CoreStory 找跨事务操作来定位 candidate：当前是否跨事务、需要何补偿动作、严格 vs 最终一致。
HITL 门禁：每次抽取前 工程负责人要在服务边界、数据拆分计划、ACL 设计、中检通过后才放行某次抽取。第一次抽取尤其重要——它奠定后续抽取的模式。

最佳实践（最易踩的坑）

  • 先抽最小、可行的服务（低耦合、清晰所有权、消费者少）以增长模式肌肉记忆。
  • 别第一天就拆库——先从共享 schema ownership 起步，边界稳定后再拆。过早拆分是惯用失败。
  • Facade 是你的安全网——投资百分比路由、熔断、请求镜像。
  • 从第一天就按可独立部署设计（独立 CI、config、DB migration、监控——否则做出分布式单体）。
  • 契约测试不可让步（Pact、Spring Cloud Contract）。
  • 为"数据税"做预算：共存期双写或数据同步复杂且临时，必须计划并设计拆除。
  • 用业务指标兜底（下单完成率、支付成功率、转化率），不止技术指标。
