Lesson 13 · 测试与验证

Spec-Driven Test Generation（规格驱动测试生成 · 总纲）

多数 AI 生成的测试是"实现镜像"——在断言代码如何做，而不是做对了什么。本课拆开这个哲学问题。

镜像测试的原罪（code-mirroring tests）

大多数 AI 生成测试的路径是：读一个函数 → 猜它做什么 → 写测试来"确认代码按它自己那样做"。于是它 第一天全绿、每次重构就碎、验证不了任何意义——"循环断言化装的覆盖率"（circular assertions dressed up as coverage）。来源

# 镜像测试：断言"how"（如何调用）
def test_order_calls_minimum_check_validator():
    with mock.patch("OrderValidator.check_minimum") as m:
        m.return_value = False
        submit_order(create_order(total=4.99))
        m.assert_called_once_with(4.99)

# 规格驱动：断言"what"（结果是什么）
def test_order_rejected_when_below_minimum_amount():
    result = submit_order(create_order(total=4.99))
    assert result.status == "rejected"
    assert "minimum order amount" in result.error

第一个测试在有人改名 validator 时立刻坏；第二个测试能活过任何"保留业务规则"的重构。这就是全部差异。

CoreStory 的角色：Specification Expert（规格专家）

不镜像实现，而是先提取规格：验收标准、业务规则、不变量、授权策略、状态机定义。四个职能：行为提取（浮出验收标准/规则/状态迁移/授权矩阵/隐式行为）、约定发现（项目测试框架、目录、夹具、断言风格——生成物要跟手写的无法区分）、差距分析（哪些已测、部分测、未测）、验证（审生成的测试确实测的是"应当"而非实现细节）。

两个子 playbook 的分野

子流程范围每会话产出规模角色
Behavioral Test Coverage单模块或单域（规则/验证/授权/迁移/计算）10–30 用例（域级 30–80+）Specification Expert
E2E Test Generation关键用户旅程（全栈）5–15 场景（旅程级 3–8）Journey Expert

什么时候用 / 什么时候跳过

  • 用：有未测业务逻辑、上手安全网、重构前回归套件、合规审计、刚做完 Business Rules Extraction。
  • 跳过：实现新功能（用 Feature Implementation）、行为等价比对（用 Behavioral Verification）、纯基础设施/配置、极小型代码库（<5k LOC）。

测试质量三原则

  • Specification before Code——先向 CoreStory 提取"要测的规格"，再读源码或写测试。
  • Match conventions exactly——同框架、同目录、同夹具、同断言风格。
  • 失败断言 = 发现——断言失败（而非 setup 失败）说明"规格错"或"代码错"，值得标出给人审，别默默调断言去适配当前行为。
