Lesson 07 · 现代化阶段五

Spec-Driven Development（规格驱动开发）

为每个组件生成增量规格（delta spec）+ TDD 实现——阶段五的执行方法论，也是"第一次就写对"的方法。

现有 SDD 工具的盲区

GitHub Spec Kit、Kiro、Tessl 这类 SDD 工具擅长结构（怎么把规格写下来），但缺架构地基——它们不知道你的系统已有什么。CoreStory 的持久代码智能补上这一环：以 Expert 的身份提供 PRD/TechSpec/用户故事编码出的机构知识，以 Navigator 指出具体文件与扩展点。核心产出是 delta spec：只描述"会变化的"部分，并在实现前用架构验证它。来源

六相位

  1. Ground（地面）（Expert）— 收集需求、选项目、建长命对话 Spec: #412 - Add webhook...，然后四类基础查询：架构模式、可复用组件（reuse-first）、不变量与约束、设计历史。有阶段二清单就用 invariants + AC 字段。
  2. Specify（写增量规格） — 原则：reuse-first（先写可复用的现有组件）、invariant-first（先写"绝不能破坏的"，再写已有、只补增量）、带可测验收标准。规格节序：§不变量 → §要复用的现有组件 → §新增/修改组件 → §验收标准（引用具体组件）。
  3. Validate（验证） — 把规格提交给 CoreStory 做架构事前剖析（pre-mortem）：查模式冲突、缺依赖/下游影响、失败模式（目标 URL 不可达、峰值流量、删除中的队列项、安全）。任何 SDD 工具都做不到这一点。
  4. Plan（规划） — 把已验规格映射到具体文件、扩展点、依依赖排序的实现顺序（imports → 模型/migration → repository → service → endpoints → 注册 → 集成测试）。
  5. Implement（TDD） — 从验收标准（Given/When/Then 结果式）和不变量（后条件式："任意操作后 <不变量> 依然成立"，常做属性/性质测试）写失败测试，再逐步实现，每步都让 CoreStory 校验 <新代码> 是否符合 <模式>。
  6. Verify & Capture — 逐条验收标准（每条 → 对应测试 + 实现位置）、每条不变量（→ 后条件测试），不留"隐式信任"；提交时带架构上下文并对对话加 COMPLETED 前缀、更新工单。

增量规格的三种坏气味（为什么不做 greenfield spec）

Greenfield spec 把功能写成"代码库还不存在"的样子 → 自相矛盾、重复、臃肿、结构冗余。而 delta spec 动态适应性更好：extend EventSubscriber 之类的小改动天然跟随架构演进。

机构知识的"活"记录 规格不只是单一静态文件——CoreStory 对话本身就是"活的规格记录"（决策 + 推理），用 conversation_id 引用它。

两大支柱原则（记忆锚点）

  • Invariant-first：不变量是规格的"免疫系统"——测试失败先查不变量。
  • Reuse-first：阶段一的重用问题常能砍掉 30–50% 的规格工作量（"约 40% 的新功能规格其实描述的是已实现功能"）。

现代场景下还配套两个动作

变化时代注意：规格中引用的是"已存在的组件"，若是模板与 convention 之外的也要在"修改组件"里说明，例如给 EventBus 加订阅类型且不改既有接口。搞现代化时 AC 来自工作包等价要求 > 规则清单 AC > 仅对 [NEW]/[CHANGE] 新增 AC；[PRESERVE] 直接逐字保留旧 AC。
