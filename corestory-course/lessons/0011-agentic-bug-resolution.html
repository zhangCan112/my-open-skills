Lesson 11 · AI 辅助开发

Agentic Bug Resolution（Agentic 修 Bug）

不靠 grep 盲走代码库——先让 CoreStory 讲清"系统该怎么工作"，再写失败测试证明 bug，最后最小修复。

这正是 grep 取代不了的地方

bug 修复最贵的是"理解意图"：系统应当如何行为、有哪些不变量、为什么这样写。这些不存在于代码搜索里，只存在于 PRD、TechSpec、用户故事与代码历史的综合理解中——这就是 Expert 角色。它解决"修症状而非根因""弄坏相邻功能"的风险。来源

六相位（与 Feature Implementation 共享 DNA，起点相反：此处始于"坏了的东西"）

  1. Bug Intake & Context — 拉取工单（或要求用户给症状/复现步骤/期望 vs 实际/影响组件）；选项目、验摄取、建对话 Bug Investigation: #6992 - reset_index coord_names issue。
  2. Understanding System Behavior（Expert 关键相位） — 建"应当如何"的真值表：架构（该功能所在文件、测试覆盖、辅助模块、集成点）、不变量与数据结构（本 bug 涉及的 _coord_names 与 _variables 关系、drop=True/False 下如何更新）、历史（设计意图、相关 bug）。此相位是分水岭。
  3. Hypothesis Generation（Navigator） — 把症状翻译成指向代码路径的排名根因假设： 
    "若 bug 是 drop=True 时 _coord_names 残留陈旧条目，该看哪些具体代码路径？带我过一遍逻辑流。"
    生成"缺清理 / 状态更新错 / 其它"的概率排序。
  4. Test-First Investigation — 在读完任何实现代码前先写复现测试（不变量即断言，如 _coord_names ⊆ _variables.keys()）。测试必须失败；让它失败的同时 CoreStory 验证它确实测对了行为。再针对性读 CoreStory 指明的代码，对照期望找出 bug，并用 CoreStory 确认发现。
  5. Solution Development — 最小修复（恢复不变量即可，遵循架构模式），复现测试通过，CoreStory 校验（对齐、副作用、不变量未破），补边界用例（部分操作、空输入、参数组合、并发），跑全量无回归。
  6. Completion & Knowledge Capture — 结构化提交（Problem / Root Cause / Solution / Invariants Restored / Testing / References），置 resolve，改名 Bug Investigation: #4821 - RESOLVED - ...。

一个真实示例拆解（xdArray 术语）

Bug: reset_index(drop=True) leaves stale coord_names
Problem: _coord_names 在 drop 后仍含被删坐标条目。
Root Cause: line 4180 只往 coord_names 加 new_variables，却从不删 drop 掉的坐标，
             违反不变量 coord_names ⊆ variables.keys()。
Solution: 在加 new_variables 前先把 drop_indexes 从 coord_names 里减去。
Invariants Restored: coord_names ⊆ variables.keys()
Testing: 新增 reset_index_drop_cleanup + 3 个边界用例；全量无回归。

为什么"先失败测试"是铁律

五个字：失败证明存在，通过证明修复，同时防复现。若测试意外通过 → 说明 bug 不是你以为的那样 → 回到阶段二。省掉它等于给每次都靠猜。
