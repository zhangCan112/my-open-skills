Lesson 06 · 现代化阶段四

Decomposition & Sequencing（分解与排序）

目标架构有了，问题变成：怎么抵达而不在半路把一切都弄坏？

核心概念：Work Package（工作包）+ TCE 循环

本阶段把现代化愿景拆成一组可独立部署的工作包，并按依赖排序。每个工作包都围绕 Transform → Coexist → Eliminate（TCE） 组织——这是 Strangler Fig（Martin Fowler, 2004）的操作化表达：先建新版（Transform），新旧同时跑并用 facade 路由流量（Coexist），行为验证通过后退役旧版（Eliminate）。来源

为什么排序比想象难 不能只挑"最容易的"组件先做——若它和另三个共享一张数据库表，立刻撞上数据分解难题；也不能盲从依赖图——高风险组件该早做（早消风险）还是晚做（先学容易的）取决于团队风险偏好。正确顺序平衡：依赖约束、风险偏好、业务价值交付、团队能力。

六步工作流

  1. Input Loading — 载入 ADR 与依赖分析；建 [Decomposition] 系统名 - Migration Planning 对话。
  2. Component Decomposition — 找出迁移单元（最小可独立部署集合）： 
    "哪些组件共享无法拆分（或须两侧同时迁移）的数据库表？哪些有同步调用依赖、单边现代化就会断？哪些共享业务逻辑？把组件分组为可独立部署的迁移单元。"
    并验证每个单元真的能独立运行 + 有回滚路径。
  3. Dependency Mapping — 硬依赖（必须先完成，如 API 由对方提供）vs 软依赖（先做更顺、但可加临时集成点独立进行）vs 共享基础设施。识别关键路径。 
    "对每个工作包列出对其他包的依赖：硬依赖（WP-X 必须等 WP-Y）、软依赖、共享基础设施依赖。绘制依赖图，找出决定最小总时长的关键路径。"
  4. Sequencing — 依依赖 → 风险 → 业务价值 → 团队容量排序；识别快速取胜（低耦合、高就绪、高价值、少依赖——第一个 sprint 打样用）；识别可并行的工作包；逐位做风险分析。这里最依赖工程判断。
  5. Work Package Definition — 每个工作包给出 Transform（delta spec 范围、目标模式、文件数、测试策略）/ Coexist（facade 方案、数据同步、回滚计划、验证标准）/ Eliminate（退役清单、facade 拆除、最终验证）+ 五类验收标准。
  6. Ticketing Integration — 有 Jira/Linear MCP 就推进去（epic + story + 依赖链接）；没有则输出结构化定义手动导入。

TCE 与另外两种执行模式

模式何时用要点
Strangler Fig默认；可拦截流量时Transform → Coexist（facade 路由，可秒回滚）→ Eliminate
Branch by Abstraction内部共享库/数据访问层无法拦截引入抽象层 → 新旧实现并存 → 逐个切调用方 → 删旧实现
Parallel Run（影子流量）支付/合规/财务等高风险逻辑生产请求双写，差异率低于阈值（关键服务 <0.01%，一般 <0.1%）才切换

共存期数据同步：可用 CDC（Change Data Capture）（Kafka/Debezium）避免双写问题，实时同步新旧数据存储。

HITL 门禁 第 4 步排序后：工程负责人审阅迁移序列、工作包定义、依赖图，批准后才推进 Jira/Linear。排序即团队排班，必须人来确认。

产出：Work Package 模板骨架

ID / Component / Strategy / Migration Unit / Dependencies / Blocked by / Sequence Position / Effort。每段拆 Transform · Coexist · Eliminate 子块，结尾 Acceptance Criteria（功能、行为等价、性能、集成、运维五类勾选）。

最佳实践

  • 按依赖链排序，不是按"以为的难度"。
  • 用快速取胜开局——第一次增量迁移建立团队信心与组织支持。
  • 别低估临时集成工作（防腐蚀层、适配器、数据同步——是真实工程活）。
  • 基础设施提前当作"Step 0"工作包（API 网关、事件总线、service mesh、CI/CD）。
  • 开工前先定义"完成"；Coexist 是你的安全网，别急着过。
