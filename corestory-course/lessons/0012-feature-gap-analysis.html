Lesson 12 · AI 辅助开发

Feature Gap Analysis（功能差距分析）

在已有代码库上加新功能几乎都不是绿地——先系统化标出"已有 / 缺失 / 需改动"，写代码前心里有底。

为什么需要"差距分析"扮演者

给成熟代码库加功能，主干成本在于弄清新功能与现状的交互：数据模型要加哪些字段、哪些 UI 组件要改、扩展/冲突了哪些业务规则、哪些集成点要更新。CoreStory 在此多了一个独特角色 Gap Analyzer：把功能规范与系统逐项比对，指向具体文件/函数。来源

四相位

  1. Context Loading（Expert）— 建 Gap Analysis: <Feature Name> 对话，取 PRD/TechSpec，把功能规范抛给 CoreStory 定向定位最相关子系统： 
    "我要实现一个新功能：[粘贴 spec]。 现有代码库中与本功能最相关的子系统/模块是哪些？有没有相似模式的已有功能？主架构模式是什么（MVC / 事件驱动 / 微服务）？"
  2. Gap Identification（Gap Analyzer 核心）— 七类全量一查（见下表），逐类带文件路径 + 开发者级改动描述；对稀疏类目追问（能再挖细一点吗）、对跨类目影响（链式）识别。
  3. Validation & Completeness（Expert + Navigator）— 让 CoreStory 复核是否遗漏文件/下游影响、是否与既有模式冲突、给依赖排序与范围汇总（新建 vs 修改文件数、最高风险项、哪些可延后）。
  4. Implementation Planning（Navigator）— 依依赖分组（数据模型 → 业务逻辑 → UI → 渲染/输出 → 集成），每组列出文件、改动、模式、测试、依赖。改名 Gap Analysis: <Feature> - Complete。

七类 Gap（记忆手枪扳机）

#类别示例问题
1现有可复用能力哪些能原样复用？
2数据模型缺口要加哪些字段/表/枚举？
3UI 缺口哪些界面/组件要更新？
4业务逻辑缺口哪些规则要新增/改？
5渲染 / 输出缺口导出/打印/响应格式？
6集成缺口哪些外部系统/API 要接？
7约束缺口哪些非功能/约束要满足？

每条 gap 有 ID（DM-001、UI-001、BL-001、RO-001、IG-001、CG-001）并记录"当前状态 / 目标状态 / 依赖"。

产出：Feature Gap Analysis Report

Executive Summary → 7 类 gap 表 → Cross-Cutting Concerns → Scope Summary（文件数/风险/延后项）→ 依赖序实施计划。用"活文档"心态持续更新。

最佳实践

  • 先全量七类扫一遍，再向下钻到稀疏类目；大功能拆子功能分开查。
  • 模式冲突要显式标记，别无声制造例外（问是延展现模式还是合理化新模式）。
  • 优先级：数据先（下游都依赖），再业务、再 UI/渲染、集成最后。
  • spec 变了就重跑分析；善用 list_conversations 追踪演化。
