Lesson 09 · 现代化阶段六

Behavioral Verification（行为验证）

证明"新代码确实做着旧代码做过的事"——现代化项目的成败就在这一步。

开篇的悖论

现代化失败不是因为团队读不懂旧代码，而是因为无法证明新代码与旧代码行为一致。而 "not every behavior should be preserved——有些是 bug" 这个判断本身需要人。因此阶段六的核心动作：以阶段二 Business Rules Inventory 为行为契约，逐规则验证，而不是对着一堆含 bug 的旧代码逐行对比。来源

五步内部流程（阶段六的内部步骤）

  1. Setup — 从 RESOLVED - [Business] 对话取规则清单；为 [Verification] 系统名 - 组件名 建验证线程；把清单收窄为"本组件适用的规则"（直接实现 / 作为工作流一部分 / 依赖它 / 跨切面）。
  2. Rule-by-Rule Verification — 逐条规则追溯到现代化实现（找到文件/函数/行区间，判定直接 vs 分散、直接 vs 间接执行），比较行为语义（输入条件、逻辑、副作用、错误处理、输出），分类为 Equivalent / Improved / Different / Missing。对含糊/带 bug 的旧规则，问"这行为是有意的吗？保留 bug 还是修掉？"默认保守：无批核就保留旧行为。
  3. Edge Case & Invariant Testing — 边界条件（null/空、极值、并发、时区/闰年、货币舍入与浮点、状态边界）在新旧各测一遍；验证系统不变量被保留；再测隐式行为（默认值、顺序保证、时机/重试/限速、审计轨迹、错误消息格式）——"隐形回归"的来源。
  4. Integration Point Verification — 对比 API 契约（端点、方法、请求/响应格式、HTTP 码、分页/排序/过滤、认证要求）与数据格式/编码（字符集、日期、数值精度、null 处理、序列化）；分析下游消费者受影响与 Coexist 中 facade 如何翻译。即使新增可选字段也标出。
  5. Equivalence Report — 汇总为 Behavioral Equivalence Report；改名 RESOLVED - [Verification]...。

四层验证策略

层级是否需要运行方法示例
Tier 1 静态否规则追踪、不变量检查、数据流对比、边界用例生成。CoreStory 最强项（同时理解两个代码库）。
Tier 2 动态是刻画测试（Golden Master）、契约测试
Tier 3 生产级需要类生产环境影子流量测试、记录回放（record-replay）
Tier 4 数据迁移若涉及迁移行数、校验和、语义校验、参照完整性
刻画测试 / 金标（Characterization Testing） 由 Michael Feathers《Working Effectively With Legacy Code》提出：对旧系统抓取一套全面输入的输出作为"金标"，现代化实现必须逐一对齐——旧系统的行为就是规范。工具：ApprovalTests 等。
HITL 门禁：等价签字 报告须经领域专家或工程负责人确认（规则全等价、差异可接受、缺规则已处理）后才允许退役旧组件 / 进入 Eliminate。等价报告：Ready for Eliminate / Needs Remediation / Needs Domain Expert Review 三态之一。

报告骨架

Summary（范围内规则计数 + 各状态）→ Rule-by-Rule Verification（Rule ID | 旧位置 | 新位置 | 状态 | 备注）→ Behavioral Differences（分类：Intended improvement / Acceptable deviation / Regression）→ Missing Rules → Edge Case Findings → Integration Point Verification → Invariants Verified → Recommendation + 签字清单。

最佳实践

  • 对着清单验证，不是逐行旧代码——后者包含 bug、workaround、死代码。
  • 先分类再修：不是每个差异都是 bug（改进/退化要分开，只有 regression 才修）。
  • 涉及含糊规则要请领域专家；别跳过集成点验证；隐式行为要测（清单里看不到）。
  • 按功能区分批验证；让验证把置信度从 Hypothesized 升级到 High-confidence / Verified。

随堂测验

不需运行代码、靠规则追踪与不变量检查的是哪一层？

发现旧实现有一个 bug，新实现"修好了它"——这是什么？
