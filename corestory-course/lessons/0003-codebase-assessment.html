Lesson 03 · 现代化阶段一

Codebase Assessment（代码库现代化就绪度评估）

每场现代化都从同一个问题开始：到底在跟什么东西打交道？

为什么需要系统化评估

用人脑走查几份源码 + 架构师访谈，得到的是"大家以为系统长什么样"的快照。部落知识只能覆盖常改动的 20%——剩下 80%（每月跑一次的批处理、没人记得的集成点、七个服务悄悄依赖的公共模块）藏在系统性排查之前。CoreStory 摄取并语义理解整个代码库，给你一个能对着全系统（不是抽样）回答具体架构问题的 Expert。来源

关键原则：Expert before Navigator

先问"这套系统应该怎么工作"（设计架构、数据流、集成模型），再去找"哪里出问题"。这个架构基线让偏差、捷径、耦合热点、技术债都更容易现形。

六步工作流

  1. Setup & Orientation — list_projects 确认目标；get_project_prd/get_project_techspec 取架构语境；建名为 [Assessment] 系统名 - Modernization Readiness 的对话线程。
  2. Architecture Mapping — 组件清查、通信模式、数据存储、入口点，以及（对大型机）非代码工件：JCL、copybook、CICS、VSAM、排序工具控制语句、系统出口、存储过程。扫描架构： 
    send_message: "提供此系统的主要组件、服务与模块完整清单。对每个组件，说明用途、技术栈、近似规模。按逻辑域或边界上下文分组。"
  3. Dependency Analysis — 内部耦合、共享数据存储、外部依赖、集成点脆弱性。这一步直接喂给阶段四。 
    "哪些组件共享数据库表或数据存储？列出每个共享资源的所有读写组件。是否有跨组件边界的外键？"
  4. Tech Debt & Risk — 技术债、安全隐患、合规缺口、测试性、运维复杂度。每项都要严重度 + 爆炸半径，且一定带文件路径。
  5. Readiness Scoring — 每个组件 1–5 分（5=马上能改，1=完全不行），并建议 7 Rs 策略——按组件，不是全系统一刀切（53% 企业走混合策略）。
  6. Report Generation — 综合成 Modernization Readiness Report；对话改名 RESOLVED - [Assessment]...。

评分标尺

分数含义
5可以直接现代化（低耦合、好测试覆盖、清晰边界）
4小准备即可（解一些耦合、补一些测试）
3需中量准备（共享数据存储、中度耦合、测试有限）
2需大量准备（深度耦合、无测试、与多组件共享状态）
1未就绪（极端耦合、无测试、文档化不足、合规阻碍）
HITL 门禁 报告须经技术领导审阅作 Go/No-Go 决定后才进入阶段二/三。没批准的评估会一路放大错误——不可跳过。

最重要的产出：Modernization Readiness Report

固定结构：Executive Summary（就绪度、组件数、策略分布、Top 3–5 findings）→ Architecture Map → Dependency Graph → Tech Debt Inventory（TD-001...）→ Risk Register（RR-001...）→ Component Readiness Scores → Recommended Modernization Sequence → Prerequisites & Blockers。全部带文件级证据。

最佳实践速记

  • 先看合成规范再提问：用 TechSpec 词汇让查询更具体。
  • 每组件都评估，哪怕你以为你了解它——惊喜总在系统化之后。
  • 别漏非代码工件：大型机会省掉 30–50% 的范围。
  • 永远要文件路径；低测试覆盖是阻塞项不是脚注（没基线就没有"正确"定义）。
  • 诚实地打分——Retain 是合理的结局，好评估同样靠"阻止不必要现代化"省钱。
