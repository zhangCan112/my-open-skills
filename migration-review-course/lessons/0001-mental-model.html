Lesson 01 · Mental Model

迁移 review 的本质：行为等价，不是语法等价

先换脑子，再学方法。这一课是最重要的一课。

为什么逐段对比会漏

拿到一个"代码迁移"（重写、换框架、换语言、拆微服务），人脑最自然的做法是：看 diff，逐行确认"长一样"。这就是第一坑。

迁移的目标从来不是"代码长得像"，而是行为等价（behavioral equivalence）——旧代码做什么，新代码就必须做什么。语法像不像完全不重要。

Michael Feathers 在 Working Effectively with Legacy Code 里点破了这条铁律：旧系统跑在生产上的行为，本身就是规格（specification）。包括它的 bug、它的 workaround、它的默认值——用户依赖的正是这一切。迁移时"顺手修掉的 bug"可能就是一个业务依赖。

本轮课程的口诀：审迁移，不审"改动"，审"行为全集是否完整搬移"。

两个会骗你的事实

  • 语法等价 ≠ 行为等价。一个 == 改成 ===、一个 ArrayList 换成 LinkedList，diff 几乎一样，行为可能全变。
  • diff 对比天然看不到"丢掉的"东西。旧代码有个分支、新代码整段没写——这不产生任何 diff。遗漏（missing behavior）在纯 diff 视角下是不可见的。

三类会被漏掉的"隐形行为"（预热）

后续 6 课会反复用这些词，这里先建立直觉。迁移中最容易丢的是这些东西：

类别它长什么样为什么 diff 看不到
默认值 / fallbackvalue ?? "todo"、空态、默认分支删掉逻辑时，整行一起没了
顺序保证结果排序、for 顺序、字典序新实现"看起来也对"，只是次序不同
时序 / 日志 / 错误格式超时、重试、审计日志、错误码、错误文案下游靠它解析，看不到就崩

第 4 课会专门展开。现在只需要记住：审查不是"读一遍新代码"，是"把旧代码的每个行为列出来，再去新代码里一个个找回来"。

一分钟小任务

不用写代码。看着下面这段"旧代码"里的 20 元以下免邮 规则：

function shippingFee(cart) {
  if (cart.total < 20) return 0;      // 免邮
  if (cart.total < 100) return 8;     // 常规
  const express = cart.selected_express; // 默认 false
  return express ? 30 : 15;
}

新代码如果只有 split_20 → 0 和 split_100 → 15 两个字（表达式）而丢了 express——diff 完全看不见，业务却变了。写下你发现的"旧代码有而 diff 看不见"的行为，下一课我们会把它变成清单。

Quiz

一段代码从 Python 重写为 Java，diff 完全不同，界面完全一致。这时 review 的第一步应该是什么？

对。先枚举旧行为的全集——这是 parity-check 和 CoreStory 的共同起点，也是本课程的方法论地基。
