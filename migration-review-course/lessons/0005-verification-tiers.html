Lesson 05 · Verification Tiers

验证方法分四层：从静态解析到生产流量

手动 review 只是第 0 层。真正的验证从"玩真的"开始

前面的课建立了清单（第 2 课）、分类（第 3 课）、隐形行为（第 4 课）——这些全是静态审查。静态审查的最大弱点是"看起来都对，跑起来才崩"。所以一线实践（GitHub 的 Crane、AWS 的 Transform、CoreStory 的 playbook）都把验证分成四层，越往下越接近"新旧代码真刀真枪对打"。

四层验证方法

层名字做法能证明什么
Tier 1 静态行为比对 你的知识清单 + 旧新代码对照（第 2~4 课的成果） 行为全集"看起来"完整
Tier 2 Characterization（表征）测试 用真实输入在旧系统跑出输出，存成"黄金标准"（golden master），新系统必须逐条对上 给定输入，新旧输出逐字节一致
Tier 3 Shadow / 影子流量对比 生产流量同时打旧、新两套，对比每个响应，不一致的告警 在生产真实负载下行为一致
Tier 4 数据对账（Reconciliation） 迁移后对比新旧数据：行数、校验和、派生字段、外键完整性 迁移后数据真实无损（不是"再跑两遍就是一样的"）
关键思想（Chesterton's Fence）：没有 Tier 2+，说"我们把业务逻辑完整搬了"可能只是 wishful thinking。Characterization 测试用"旧系统输出 = 规格"。这是唯一能跳过"需求文档说不清、代码就是事实"困境的办法——旧系统跑出来的才是权威基准。

怎么做出 Tier 2 的黄金基准（golden master）

  1. 选定一个业务函数或工作流。
  2. 喂一组真实或构造的输入（覆盖边界值、错误路径、典型场景）。
  3. 在旧系统上运行，捕获输出——这就是 baseline。
  4. 为每对 (输入)→(输出) 写成断言。
  5. 跑新系统，把新旧输出逐字段 diff。

这里的细节很讲究：数字容差（浮点 / 舍入差异要不要一刀切）、字段级别对比（不能只输出 pass/fail）。第 6 课会讲怎么处理"故意不同"（修复 bug 后基准改了怎么办）。

Quiz

银行迁移项目，你担心迁移后"状态机流转"在极值 case 下出错。最高效的验证方法是什么？

状态流转的诡异 case 靠人读不出来——用 Tier 2（表征）构造覆盖 + Tier 3（影子）在生产流量下验证。单测用例多不代表覆盖到。
