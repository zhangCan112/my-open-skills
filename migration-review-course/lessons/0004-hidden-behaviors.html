Lesson 04 · Hidden Behaviors & Invariants

最容易漏的：隐形行为与不变量

diff 不会告诉你这些，但它们最容易让迁移上线即崩

什么是"隐形行为"

第 1 课留了个钩子：默认值、排序、时序、日志、错误格式。这些行为不会出现在任何 diff 里——它们散落在"看似显然"的实现细节中，直到下游或真实用户在迁生产踩雷。CoreStory 把这类东西明确列为验证对象：

  1. 默认值——可选参数缺省时旧代码返回什么？fallback 分支是什么？
  2. 排序保证——接口返回的顺序是否是下游依赖？迁移后顺序变了，下游静默错乱
  3. 时序行为——超时、重试、速率限制
  4. 日志 / 审计——迁移后审计记录还在吗？合规还要靠它
  5. 错误格式与错误码——下游有没有解析你的错误文案或 status code？
一句话：Diff 只会告诉你"代码变了"，不告诉你"外卖没变但行为变了"。隐形行为清单就是专门盯这一类的。

不变量（Invariant）：系统级的地基

不变量是"任何时候都必须成立"的约束，往往不写在任何需求文档里，只在代码里被隐含执行：

  • "余额永不为负"
  • "订单状态只能单向流转：pending → confirmed → shipped → delivered"
  • "所有时间戳统一存 UTC"
  • "每条 line item 属于且只属于一个订单"
  • "created_at 永不晚于 updated_at"

为什么单独拎出来？因为单条规则可以各自正确，合起来的系统行为却变坏了。不变量是"整体约束"，单独逐条验证每个方法会漏掉它们的互动。

操作口诀：为每个模块做一次"隐形行为盘点"

在做正式清单（第 2 课）时，加一轮特别扫描：

  1. 读出模块的所有默认值与 catch-all else 分支，列出来。
  2. 找出所有排序保证点（SQL ORDER BY、for 遍历顺序、序列化字段顺序）。
  3. 找出所有（外部可见）错误文本 / 错误码 / HTTP 状态。
  4. 列出模块写入的日志 / 事件 / 审计记录。
  5. 把系统级不变量写成断言，纳入验证 check-list。

Quiz

旧系统：金额用 double 存两位精度，写成 JSON 输出。新系统改用 BigDecimal，正确但 JSON 输出的小数位有时多一位。下游某报表直接拼接这个数字。这最接近哪类问题？

行为都在，但输出格式（一种显式的隐性契约）变化，下游会崩。归在"数据格式/序列化"这一类隐形行为，而不是功能 MISSING。
